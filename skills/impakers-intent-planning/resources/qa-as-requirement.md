# QA-as-Requirement

QA는 구현 후 검수 체크리스트가 아니라 요구사항의 성공 기준이다. Intent Planning 단계에서 QA를 먼저 쓰면 기능의 범위와 성공 관찰 방식이 명확해진다.

## 작성 규칙

- "테스트한다" 대신 사용자가 관찰할 성공 결과를 쓴다.
- 입력, 시스템 처리, 저장/표시 결과, 실패 상태를 한 문장에 포함한다.
- 자동화 가능 여부를 표시하되, 자동화가 불가능해도 요구사항 성공 기준은 남긴다.
- UI QA는 화면 존재가 아니라 사용자가 목표를 완료할 수 있는지로 쓴다.

## 좋은 예

- 사용자가 필수값을 누락하고 저장하면 제출이 차단되고, 누락 필드 옆에 복구 가능한 오류 메시지가 표시된다.
- 담당자가 업무를 완료 처리하면 목록과 상세 화면의 상태가 모두 `완료`로 바뀌고 새로고침 후에도 유지된다.
- 권한이 없는 사용자가 관리 API를 호출하면 데이터가 변경되지 않고 감사 로그에 차단 이벤트가 남는다.

## 나쁜 예

- QA를 진행한다.
- 버튼이 잘 동작한다.
- API 테스트를 작성한다.

## Gate

QA-as-Requirement가 없으면 vertical slice 후보로 넘기지 않는다. 단, 탐색 spike는 별도 표시하고 제품 완료 기준으로 계산하지 않는다.
